# DNN Manager 1.7.9

**Assemblies checked where they really are.** The site overview's **Assemblies** check follows `web.config` to the folders modules such as Imageflow and 2sxc keep their DLLs in, reads every folder under `bin`, and no longer reports assemblies as missing that are there.

## Highlights

### Assemblies where web.config says they are
- Modules such as Imageflow and 2sxc keep some DLLs in a folder of their own - `bin\Imageflow`, `bin\2sxc` - and `web.config` points .NET at them with `codeBase`. The **Assemblies** check didn't read those entries, so the files were reported as **Missing**, a **Version conflict** or a red **Binding redirect** although the site loads them fine.
- It now reads every `codeBase` entry and checks the file it points at. A `codeBase` whose file isn't there is reported in red as **Code base**.
- An assembly with more than one `bindingRedirect` - one per version range, as Imageflow adds for `Microsoft.Extensions.*` 2.2.0.0 - is checked against all of them, not only the first.
- Messages say which folder has which version: *the site has 8.0.0.0 in bin, 9.0.0.0 in bin\2sxc*.

### Every folder under bin
- **Assemblies** counts every DLL under `bin`, its folders too, and lists the count per folder.
- **Not loaded by ASP.NET** lists the ones in a folder .NET doesn't look in and no `codeBase` points at - a module's own, or the compiler's in `bin\roslyn`.
- When a reference is only found in such a folder, the check says where and what's missing: *bin\Imageflow has 2.2.0.0, but web.config has no codeBase for it*.
- An assembly in a folder of its own finds what is next to it, and the compiler's assemblies in `bin\roslyn` aren't checked against the site - it runs on its own.

### Assembly problems in one place
- Assembly problems are listed only in **Assemblies** on *Advanced*, no longer a second time in **Detected issues**.
- **Project health** on *General* counts them in a row of its own, **Assemblies**, so a red one still shows there.

## Other changes
- **Configuration** on *Advanced* shows how many **Code bases** `web.config` has.

## Upgrading
Install over 1.7.8 as usual. Your settings keep their format.

## Tested
- The **Assemblies** check run against five real DNN sites with 2sxc and Imageflow: on one, the eight reported problems went down to the four that really are missing - Azure Storage's references to `Microsoft.Data.Services.Client`, `Microsoft.Data.OData`, `Microsoft.Data.Edm` and `Microsoft.Azure.KeyVault.Core`, which are nowhere in the site. On another, the three Imageflow assemblies `web.config` has no `codeBase` for are named with their folder. Reading the folders under `bin` added no reports on any of the five.
- All 197 fast automated tests pass, up from 192. The new ones cover reading `web.config`'s runtime section with several `assemblyBinding`s, redirects and `codeBase` entries; assemblies loaded from a folder of their own; the same site without its `codeBase` entries; a `codeBase` whose file is gone; and a module's and the compiler's folders under `bin`.
