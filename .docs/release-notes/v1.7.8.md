# DNN Manager 1.7.8

**LocalDB projects set up on every PC.** A new project with a LocalDB file no longer fails when two LocalDB versions are installed, the Output tab marks a step as failed only when it really failed, and DNN Manager's own data survives a damaged file.

## Highlights

### LocalDB projects with two LocalDB versions installed
- A new project with database **LocalDB file** could stop at **Creating host account** with *"The database '…\APP_DATA\DATABASE.MDF' cannot be opened because it is version 998. This server supports version 904 and earlier"*. That happened on PCs with two LocalDB versions - typically Visual Studio's 2019 next to 2025.
- The cause: every Windows account has its own LocalDB, at the version it was first made with. The website's LocalDB (new, so 2025) made the database file a 2025 one, and DNN Manager then opened it in your own LocalDB, still 2019 - which can't read it.
- DNN Manager now opens a site's database file in a LocalDB of the file's own version: your own when it is that version, otherwise one of its own (`DnnManager17` for 2025), made the first time it is needed. Nothing to set up.
- It also never opens a site's file in a newer LocalDB than the site uses, which would upgrade the file for good so that the site itself could no longer open it.
- When no LocalDB on the PC can open the file, it says so in plain words, with the version to install.

### Failed means failed
- When IIS features are missing, **Checking IIS** lists them and asks whether to enable them. If you click **Enable features** and that works, the step now ends as done - not as failed.
- It is still an error when you choose **Not now**, or when a feature can't be enabled.
- *Windows needs a restart* appears only when Windows says a restart is needed, instead of after every change.

### Your settings and workspace, kept safe
- Before an update changes how DNN Manager's own database (`Documents\DnnManager\dnnmanager.db`) is laid out, it keeps a copy as `dnnmanager.backup.db` next to it.
- A damaged `dnnmanager.db` - a crash at the wrong moment, a disk error - no longer stops DNN Manager at its start, where even **Reset to defaults** failed. It is put aside as `dnnmanager.damaged-<date>.db`, and DNN Manager carries on from the copy, or with the defaults; the Output tab says which.
- An older DNN Manager started after a newer one leaves the newer one's database alone and says so, instead of writing into it.
- Fixed: a rare case where the database could be left unusable when two parts of DNN Manager created it at the same moment.

## Other changes
- SQLite, which keeps DNN Manager's own data, is version 3.53.3 - with the fix for CVE-2025-6965.

## Upgrading
Install over 1.7.7 as usual. Your settings keep their format.
- This release only has `DnnManager_Setup-1.7.8-x64.exe` and `DnnManager_Portable-1.7.8-x64.exe`, no copies under the old names. DNN Manager 1.7.7 updates as usual; 1.7.6 and older can't install it with **Update** - download it from GitHub once.
- A project that failed with the *version 998* error stays as it was: remove it (**Remove…**) and create it again.

## Tested
- On a real LocalDB 2025: DNN's own database file opened through your own LocalDB when it is the file's version, and through a new `DnnManager17` instance of its own when it isn't - made the first time, used again the next.
- All 192 fast automated tests pass, up from 180. The new ones cover which LocalDB version opens which database file and reading the version from the file itself; twelve threads creating DNN Manager's database at once (which failed before this release); a database from a newer version left untouched; the copy before the tables change; a damaged file put aside and brought back from that copy; **Reset to defaults** on a damaged file; and the SQLite version.
