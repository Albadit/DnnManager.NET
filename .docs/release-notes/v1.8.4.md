# DNN Manager 1.8.4

**A live site's database backs up again.** A project made from a live site's backup could not be backed up or exported: the database export stopped with *SQL71501*. It now goes through.

## Highlights

### Backups and exports of a live site's database
- A database restored from a live site keeps its host's user, such as `__shop`. Exporting it stopped with *Error SQL71501: User: [__shop] has an unresolved reference to Login [__shop]*, and the backup was undone.
- This stopped **Export → Site and database (.zip + .bacpac)** and **Database (.bacpac)**, **Export → For deployment…**, and the backup **Upgrade DNN…** makes before each step.
- A `.bacpac` holds the login of every user in the database, and the site's own login (`dnn_shop`) sees no login but its own. A database on the local SQL Server container is now exported as the container's user (`sa` by default), which sees them all.
- A database on another server is still exported with the login its `web.config` names. When that login can't see one of the database's logins, the error now says what to do: export as a sysadmin (or a login with VIEW ANY DEFINITION), or drop that user if the site doesn't use it.

## Upgrading
Install over 1.8.3 as usual. Your settings keep their format.
- A `.bacpac` exported from the SQL container now also holds the logins of the host's users, such as `__shop`. Restoring it on another SQL Server makes those logins with a random password, as it already did for DNN Manager's own `dnn_` logins.

## Tested
- A real site's database restored from a live site's backup, with the host's user `__ceesboer`: signed in as the site's own login, only `sa` and that login are visible, which is why the export failed. Exported as the container's `sa`, the export succeeds, and the `.bacpac` holds both logins and both users.
- All 473 fast automated tests pass, up from 472. The new one checks which login an export signs in with: the container's user for a database on the container, and the `web.config` login for a database elsewhere.
