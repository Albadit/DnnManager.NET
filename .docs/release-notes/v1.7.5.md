# DNN Manager 1.7.5

**Upgrade DNN, the safe way.** DNN Manager upgrades a project along DNN's own upgrade path, one version at a time, with a backup before every step and the site put back if a step fails - and the command palette remembers the commands you ran last.

## Highlights

### Upgrade DNN
- **Upgrade DNN…** on a project's **DNN** tab, its right-click menu, the **⋮** on Details or the command palette upgrades it the way DNN's suggested upgrade path says: through every version it lists, never straight to the newest. From 9.3.2 to 10.3.3 that is 9.13.9, then 10.2.5, then 10.3.3.
- Before anything changes, DNN Manager analyses the site and shows the plan: each step and what it checked - .NET Framework and SQL Server versions (DNN 10 needs 4.8 and SQL Server 2017), extensions built for an older DNN or still using Telerik, your own web.config settings, free space for the backups. While anything blocks, the upgrade doesn't start.
- Each step: a backup of the site and its database, DNN's new files (from DNN 10.2 on as DNN's own upgrade puts them in), DNN's upgrade, a restart, then checks - nothing lost, and every portal's pages answering.
- If a step fails, or you cancel, the upgrade stops and the site goes back to the last version that worked. The Output tab says which step failed, the likely cause and what to do, and DNN's logs are kept with that step's backup.
- Every step's backup stays, and **Restore backup** names them, such as "Before upgrading DNN 09.13.09 → 10.02.05".

### Restore a backup
- **Restore backup** on a project's right-click menu, the **⋮** on Details or the command palette lists its backups with the site and the database, newest first.
- The chosen one replaces the project's files and its database. Files added since the backup are deleted; `.git` and what `_backup.filter` lists aren't touched.
- The backup's database is imported under a name of its own first and only then takes the place of the project's, so a failed restore leaves the project's database as it was.

### Recently used commands
- The command palette lists the commands you ran from it first, marked *recently used*, then the *other commands* - as in VS Code.
- They stay first while you search, and DNN Manager remembers the last 8 for the next start.

### Choose the project every time
- A project command in the command palette, such as **Rename project…** or **Edit host names…**, now always asks which project, also when a project is selected or its details are open.
- The selected project is listed first, so **Enter** picks it. Shortcuts such as **F5** still act on the selected project straight away.

## Other changes
- The command palette no longer lists **Show all commands**, since it is already open. **Ctrl+Shift+P** still opens it.

## Upgrading
Install over 1.7.4 as usual. Your settings keep their format.
- Upgrade DNN needs the site's database on a SQL Server (the local container too) - a LocalDB file can't be backed up first. Change its connection on the **Database** tab before upgrading.

## Tested
- Upgrade DNN was run on real sites by DNN Manager's own code, with DNN's packages from GitHub, IIS Express and SQL Server 2022:
  - As you would use it: a **New project** at DNN 7.4.2, 8.0.4, 9.1.1, 9.13.9 and 10.2.5, each then taken by **Upgrade DNN** through every step to 10.3.3. All passed; from 7.4.2 that is six steps in 12 minutes.
  - A DNN 9.3.2 site with three users, a role, two pages, an HTML module, a second portal and a web.config setting of its own went through 9.13.9 and 10.2.5 to 10.3.3. Every step passed its checks, nothing was lost, the host and the user signed in after each step, and the setting was kept.
  - A step made to fail (a database trigger refusing DNN 10.3's version), on a database that had been imported from a `.bacpac` before, stopped the upgrade, named the failed database command and its error, and put the site back on DNN 10.2.5, where it still worked.
- A first run on a real IIS site failed: DNN's installBlocker.lock was still held by IIS's worker process, and putting the backup back then collided with the database's file names. Both are fixed, and the tests now cover them.
- These runs found what the upgrade now handles: DNN's upgrade package breaks a 10.2+ site, DNN leaves its lock behind and holds it open, and DNN 8, 9 and 10 each remove pages and modules of their own.
- All 170 fast automated tests pass, up from 128. New ones cover the upgrade path, the analyser's rules, DNN's binding redirects, reading DNN 9 and 10 logs, the item-by-item content check, the order of lines on the Output tab, the recently used commands and Restore backup.
